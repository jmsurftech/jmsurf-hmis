# Tenancy defence in depth: Postgres row-level security plan

## Today (layer 1 + guard rail)
1. **Application filter.** Every query takes `tenantId` from the JWT (`@CurrentUser().tenantId`) and filters on it (docs/CONVENTIONS.md).
2. **Prisma tenant-scope assertion** (`apps/api/src/prisma/tenant-scope.ts`). When `NODE_ENV !== 'production'`, a Prisma middleware logs a warning (once per model and action, with the call site) whenever `findMany`, `findFirst`, `count`, `aggregate`, `groupBy`, `updateMany` or `deleteMany` runs on a model that has a `tenantId` column without a `tenantId` filter. It never blocks. Turn it off with `TENANT_SCOPE_CHECK=off`. The tables `Tenant`, `User`, `AuditEvent`, `RefreshToken` and `SubscriptionInvoice` are exempt because they are platform or identity tables.

## Planned: layer 2, Postgres RLS
1. **Roles.** Migrations run as `hmis_owner`. The app connects as `hmis_app`, which has `NOBYPASSRLS` and is not the table owner. Platform jobs (crons, super-admin, webhooks) use `hmis_platform` with `BYPASSRLS`, on a separate Prisma client.
2. **Session variable.** A request-scoped Prisma extension wraps each operation in an interactive transaction: `SELECT set_config('app.tenant_id', $1, true)` followed by the query. The `true` makes the setting transaction-local, which keeps it safe with PgBouncer in transaction mode. `tenantId` comes from AsyncLocalStorage, which the JWT guard populates.
3. **Policies** for every table that has `"tenantId"`, generated by a migration script from `Prisma.dmmf`:
   ```sql
   ALTER TABLE "Patient" ENABLE ROW LEVEL SECURITY;
   ALTER TABLE "Patient" FORCE ROW LEVEL SECURITY;
   CREATE POLICY tenant_isolation ON "Patient"
     USING ("tenantId" = current_setting('app.tenant_id', true))
     WITH CHECK ("tenantId" = current_setting('app.tenant_id', true));
   ```
   If `app.tenant_id` is unset, `current_setting(..., true)` returns NULL, so the policy matches no rows. A missing context fails closed.
4. **Rollout.** (a) Ship the extension while connecting as the owner role, so RLS has no effect yet. (b) Enable the policies in staging with `hmis_app` and run the e2e suite. (c) Watch for "0 rows" anomalies through the tenant-scope warnings. (d) Switch production to `hmis_app`.
5. **Costs.** Each query gets one extra round trip because of `set_config`, and `$transaction` batching cannot nest. Add `"tenantId"`-leading composite indexes so the policy predicate stays index-friendly; most tables already have them.
